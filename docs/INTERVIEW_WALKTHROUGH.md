# Five-minute interview walkthrough

This walkthrough matches the current UI. The simulator is random, so do not promise that a chosen click will always fail. For a reliable failure demonstration, switch Offline on before a save, show the error, switch Offline off, and retry. For partial bulk outcomes, set the failure rate high and say results are probabilistic; if the run has no failed rows, use the offline request failure to demonstrate recovery rather than pretending it was partial success.

## Demo preparation

1. Start the app and let initial 50k generation/load finish before the interview. Keep browser devtools closed unless asked.
2. Confirm the simulator starts online, stage table is visible, and the first example appears as expected. Avoid resetting the page during a bulk request.
3. For a deterministic failure story, switch Offline on, make one stage change, switch Offline off, then use Retry. Note that the initial retry may simply report synchronization depending on current row state; use a record with a pending retry state.
4. For partial bulk failure, set 40% failure and select a small group, but explain the outcome is random. If every record succeeds, do not fabricate a failure; explain the test-backed flow and show offline failure separately.
5. For a conflict, select the row first, simulate teammate edit, then attempt a stale local write before Sync. The simulation's exact timing is not guaranteed; explain the expected version 1 → 2 sequence if timing prevents a visible conflict.
6. If a demo action behaves unexpectedly, narrate the implementation and use the code/test as evidence rather than claiming a deterministic result.

## Likely questions after the demo

- Why is the full data client-side if the list is virtualized? Answer: this assignment simulates one local dataset; virtualization controls DOM cost only. Production would query and paginate on the server.
- Does this support actual simultaneous users? Answer: no. The fake API models an authoritative server map and versions in one process; a real backend must enforce the version atomically and broadcast/poll changes.
- What is the largest correctness risk? Answer: bulk undo failure recovery currently clears its snapshot even if some rows fail, and the mixed partial-result path lacks a deterministic direct test.
